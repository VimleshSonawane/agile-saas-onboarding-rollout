# Project Charter — Agile SaaS Onboarding Rollout

**Type:** Self-initiated project, simulated scenario
**Duration:** 6 weeks, 3 two-week sprints
**Author role in the project:** Project Manager for the project design and delivery

## Problem analysed

In the simulated scenario, partner/client onboarding took 21 days, was manual and inconsistent, and depended on email and scattered checklists. Customers did not know what was next, internal teams did not have a single progress view, and late security review delayed launches.

## Goal created

I created a guided onboarding flow with a target of 10 days from kickoff to go-live readiness, measured in the simulated pilot by:

- Time to first value (first usable setup completed)
- Onboarding completion rate
- Support tickets in the first 30 days after go-live
- Pilot customer satisfaction on clarity and communication

These are pilot simulation targets, not real company results.

## Scope created

**In scope:**
- Account setup and guided checklist
- Data import for the most common format first, other formats phased later
- Training materials and handoff criteria
- Pilot with 2–3 simulated partner/customer profiles
- Go-live checklist and retrospective

**Out of scope:**
- Rebuilding the core product
- Pricing or contract changes
- Custom development for every partner edge case in the first release

## Stakeholders analysed

- **Sponsor:** approves scope changes and go-live decisions
- **Product:** owns the onboarding flow and backlog priorities
- **Engineering:** builds the checklist, setup flow, and import
- **Customer Success:** owns training, pilot feedback, and handoff
- **Sales / Partnerships:** owns partner expectations and kickoff
- **Security / Legal:** owns compliance review, involved from Sprint 1

## Success criteria created

1. A customer can see every onboarding stage, owner, and next step in one view
2. Training handoff has a written completion checklist, not an informal handover
3. Security review is completed before pilot go-live, not after
4. Pilot feedback is collected, analysed, and used to change at least one flow step before full rollout
5. A retrospective records what worked, what did not, and what to change next time

## Constraints and assumptions

- Simulated team and pilot customers, created for the project
- No real customer data is used
- The demo in this repo is a static front-end example, not a production system with authentication or live integrations
