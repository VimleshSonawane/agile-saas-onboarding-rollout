# Product Backlog

Methodology: Agile / Scrum. Epics are broken into user stories with acceptance criteria. Priorities reflect the project goal: a usable, guided flow first, then polish and scale.

## Epic 1 — Account setup

**Story 1.1:** As a new partner/customer, I can create an account and see my onboarding stages, so I know what is next.
- Acceptance: stages, owners, and status are visible in one view; incomplete stages are clearly marked.

**Story 1.2:** As an internal user, I can assign an owner to each stage, so accountability is visible.
- Acceptance: every stage has one named owner role; unassigned stages are flagged.

## Epic 2 — Guided onboarding checklist

**Story 2.1:** As a new customer, I can follow a guided checklist in order, so I do not miss a required step.
- Acceptance: checklist order is enforced for required steps; progress updates as steps are completed.

**Story 2.2:** As a customer, I can see what is required from me versus what the internal team will do.
- Acceptance: each step is labelled customer action or internal action.

## Epic 3 — Data import

**Story 3.1:** As a customer, I can import my core data using the most common format, so setup does not start from a blank sheet.
- Acceptance: a sample import completes with a clear success/error summary.

**Story 3.2:** As an internal user, I can see import errors in plain language, so I can help without engineering help for common cases.
- Acceptance: common errors show a fix suggestion, not only a code.

## Epic 4 — Training and handoff

**Story 4.1:** As a customer, I can access short training materials linked to each stage, so I do not need a separate training call for basics.
- Acceptance: each major stage links to at least one training note or walkthrough.

**Story 4.2:** As a Customer Success user, I can confirm handoff only when the completion checklist is met.
- Acceptance: handoff is blocked until required items are marked complete.

## Epic 5 — Reporting and pilot feedback

**Story 5.1:** As a project manager, I can see onboarding progress, blockers, and time in stage, so I can act early on delays.
- Acceptance: progress, blocker, and time-in-stage are visible for the pilot group.

**Story 5.2:** As a pilot customer, I can give feedback on clarity and blockers, so the flow can be improved before full rollout.
- Acceptance: feedback is collected per stage and reviewed in the sprint retrospective.

## Backlog notes

- Stories were refined to be small enough for one sprint, with dependencies noted in the RAID log.
- Items not selected for Sprint 1–3 are kept in a future backlog: additional import formats, automated reminders, and deeper reporting.
